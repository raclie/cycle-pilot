# 8工程の完遂とノウハウ還元

## 約束
1周は8工程すべてを回す。**定期実行、短い周回、「簡潔に記録」という指示、時間の都合は、工程を省く理由にならない。** 工程を省けるのは、次の工程に安全に進めない事情があるときだけである([cycle-delivery.md](cycle-delivery.md)の「正当な中断と復旧」)。
「簡易記録」「圧縮した記録」を1周の記録として使わない。1つの要約ファイルを書いただけでは、1周を回したことにも、1周を数えたことにもならない。

## 費用が気になるときに、変えてよい物と、変えてはいけない物

8工程は省かない。費用を下げるときは、書く量を減らす。

| 変えてよい | 変えてはいけない |
|---|---|
| 1工程に書く量（数行でよい） | 工程の数（8つ） |
| 定期実行の周期 | 工程6（還元）と工程7（観測）を置くこと |
| 1回の仕事の大きさ | 「要約1枚で1周」とすること |

## 進めない事情があるとき
権限・安全拒否、他ownerの占有、必須入力不足、利用不能な保存経路、実際の実行環境上限、ユーザーの停止指示だけが対象である。進めない工程の記録ファイルは作り、次を書く。

```
## 中断
- 事情: <何が進めないのか>
- 確認したこと: <範囲内で安全に実行できる残工程や代替保存先を探した結果>
- 保存済み/未保存: <…>
- 再開条件: <誰が何をすれば再開できるか>
```

中断した周回を「1周完了」と報告しない。進めない工程より後ろの工程が安全に実行できるなら、続ける。

## 工程ごとの大きさ
工程の内容は作業の大きさに合わせてよい。短くてよいのは**書く量**であり、工程の有無ではない。変更が不要なときは、根拠を付けた `NO_CHANGE` と書く。

## 毎周の還元(Step 6)
Step 6 は、サイクルのやり方(HOW)の見直しに加え、その周で詰まったこと・誤ったこと・初めて分かった手順を、次の担当が引ける場所へ残す。`06-engine-review.md` に次の節を必ず置く。

```
## 還元
- 事象: <何に詰まった/誤った/初めて知った> / 真因: <原因> / 次回の手順: <次に同じ場面で何をするか> / 置き先: <下の表から> / 証拠: <置いたpathかcommit>
- なし: <理由>
```

- 項目は1つ以上。無いときは「なし: 理由」。節を省略しない。
- 事象が無いと感じても、次の3問を問う。 (1) 手戻りや誤りはなかったか (2) 想定と違った事実はなかったか (3) 他の担当が同じ場面で同じ時間を失いそうか。1つでも「はい」なら項目にする。
- 誤りは上書きで消さず、訂正を追加する。

### 置き先の決め方
Step 6 の Scope 判定を使う。迷ったら狭い側に置く。

| 内容 | 置き先 |
|---|---|
| 対象システムの罠・手順 | 対象システム側の手順書。無ければ Mission BACKLOG |
| そのMissionだけで繰り返す判断 | Mission Skill |
| 同じWorkspaceの複数Missionで効く業務手順 | Workspace Skill |
| 実行主体(Codex/Claude等)固有の操作 | Executor Skill |
| 複数Workspaceで効くと**実測**で言えるもの | Global の昇格候補(`skill-federation.md` の手順で提案。直接は書かない) |
| 今回だけの指示 | 置かない(03-prompt のみ) |

置いたら、置き先のpathとcommitを「証拠」に書く。会話で言っただけは、置いたことにならない。

### してはいけないこと
- 秘密情報、専用repoのSTATE・原稿・コード・DBを共通元へ写さない。
- 1回だけの出来事を一般則として Global に書かない。
- 「なし」を機械的に並べない。「なし」が3周続いたら、Step 7 の観測(feedback_loop)として、問いが働いていないことを記録する。

## 機械の確認
この版には検査scriptを含めない。次を人が確かめる。
- 各周回の記録に、工程1〜8のファイルがあるか(無い工程は `## 中断` に事情と再開条件があるときだけ許す)。
- `06-engine-review.md` に `## 還元` 節があり、項目に「置き先」「証拠」があるか。
- 要約だけの記録で周回を済ませていないか。
- 「なし」が連続していないか。

内容の正しさ、置き先の妥当性、効果は判定しない。確認できたことを、還元できた証拠にしない。

## 効果の見方
還元した項目が、後の周回で実際に引かれて手戻りを減らしたかは、別に観測する。置いた件数や「なし」の数だけで成果としない。

## Skillの利用と改善(工程1〜3 / 5〜7)
手順の知識を担当者の頭と記録の中に溜めず、Skillに戻して育てる。
- 工程1に「## 使うSkill」(使う/参照するSkillと、足りないと予想する点)、工程3に「### 使うSkill」(不足を見つけたらその場で直すか、直す先を書く)を置く。
- 工程5に「## Skillの評価」を置く: ①使ったSkill ②改善したSkill(名前・直した内容・証拠。無ければ「なし: 理由」) ③Skill一覧(Missionの SKILLS.md)の増減(追加/廃止/統合/変更なし。変更したら SKILLS.md と履歴を更新) ④Global Skillへ還元する余地(あり/なし。「あり」はIssueでの提案など、還元の証拠を同じ行に)。
- 工程1の「使うSkill」は SKILLS.md の一覧から選ぶ。使われない・古い・重複したSkillは工程5で廃止/統合を、毎周回やるのにSkill化されていない作業は追加を、工程7で見直す。
- 還元の各項目は「対応: 実施済み <証拠> / 起票済み <票ID> / しない <理由>」を持つ。置き先と次回の手順を書くだけで終えず、改善を実施するか票にする(共有の手順書を直す権限が無いときは票にする)。
- 工程6の「## 還元」には、④で「あり」としたものを置き先「Global Skill」の項目として書く。

## 票の最終状態(工程1 / 5)
票(チケット)を動かす周回が、対応表・起票・設計で止まって完了扱いになるのを防ぐ。
- 工程1に「## 扱う票」(票IDと到達させる状態。既定は close まで)を書いた周回は、工程5に「## 票の最終状態」を置き、各票を次のどちらかで書く: `<票ID>: closed <日時・証拠>` / `<票ID>: 未close 理由: <事情> / 次の一手: <手順>`。
- 工程3に「### 計画の点検」を置き、工程2の計画の終点が close か、止めるなら事情が実測で書かれているかを、保存前に確かめる。
